# Техническое задание: OnTopReplica Profiles

## 1. Цель
Развить OnTopReplica Refactor в универсальный менеджер визуальных регионов для большого числа окон. Основной сценарий — один раз описать роли и регионы, а затем одним действием восстановить десятки OTR-реплик в нужных размерах и местах.

Программа должна оставаться внешним read-only viewer/layout manager.

## 2. Сценарии

### Mining
Типичный профиль:
- 18 окон Barge — одинаковая роль и одинаковый набор регионов;
- 1 окно Booster — роль без OTR-реплик;
- 2 окна Scout — отдельная роль и другой набор регионов.

Каждый персонаж имеет постоянный slot. Порядок запуска клиентов не влияет на расположение.

### Rampant
Типичный профиль:
- 5 Vargur — роль с несколькими репликами на клиента, например Targets, HUD, Modules;
- Support — роль без реплик либо со своим набором.

## 3. Требования к Profile Manager
Главное окно показывает:
- выбранный профиль;
- Character;
- Role;
- Slot;
- Matched window;
- Status.

Функции:
- Reload — перечитать JSON-профили с диска;
- Profiles folder — открыть папку профилей;
- Apply — применить выбранный профиль и запустить/сверить managed replicas;
- Stop replicas — остановить только управляемые текущим Profile Manager реплики;
- New profile — создать профиль через визуальный редактор;
- Edit profile — открыть выбранный профиль в редакторе;
- Auto-recover restarted clients — периодически пересобирать реплики после рестарта исходных окон.

## 4. Визуальный редактор
Редактор должен позволять без ручного JSON:
- указать имя профиля и фильтр заголовка окна;
- обнаружить запущенные окна;
- создать bindings персонажей;
- назначить каждому Role и Slot;
- добавить/удалить роли;
- добавить/удалить реплики роли;
- выбрать source region мышкой на живой DWM-копии исходного окна;
- задать размер выходной OTR-реплики;
- задать default monitor/grid layout;
- сохранить профиль.

## 5. Поведение OTR-реплики
Managed replica:
- имеет размер, заданный в профиле;
- не должна менять размер мышкой;
- если clickThrough=false, должна свободно перетаскиваться мышью за любую точку окна;
- ручная позиция сохраняется отдельно для конкретного Character + Replica;
- после перезапуска программы/клиента восстанавливается в сохранённой позиции;
- если ручной позиции нет, используется grid layout;
- остаётся borderless, если это указано профилем.

## 6. Read-only ограничения
Строго запрещено добавлять:
- forwarding кликов/клавиш в исходное окно;
- SendInput в игровой клиент;
- PostMessage/SendMessage для имитации ввода;
- DLL injection;
- DX hooks;
- ReadProcessMemory/WriteProcessMemory;
- packet sniffing;
- любую игровую автоматизацию.

DWM thumbnail, window title/class/geometry и работа с собственными OTR-окнами разрешены.

## 7. Хранение
Профили: %APPDATA%\OnTopReplica\Profiles\*.json

JSON должен оставаться читаемым человеком.
Старая схема profiles-v1 без placements должна загружаться без миграции вручную.

## 8. Надёжность
- Не выбирать окно при неоднозначном совпадении.
- Не переставлять остальные слоты при рестарте одного клиента.
- Не терять ручную позицию при auto-recover.
- Не перезапускать replica только из-за того, что пользователь её передвинул.
- Не конфликтовать глобальными hotkeys между managed workers.

## 9. Проверка
Минимальный smoke test:
1. Один source client.
2. Одна роль.
3. Одна replica.
4. Выбрать регион мышкой.
5. Apply.
6. Передвинуть replica.
7. Убедиться, что размер не меняется.
8. Перезапустить source client.
9. Убедиться, что replica восстановилась в ручной позиции.
10. Проверить mixed profile: Barge + Booster(no replicas) + Scout.
